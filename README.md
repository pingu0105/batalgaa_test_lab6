## Хэсэг A: Category-Partition гараар — `POST /transfer`

```
POST /transfer  { "from": ID, "to": ID, "amount": NUM, "currency": CODE }
201 {"result":"OK"}  ·  200 {"result":"ERROR_..."}
```

### Олон алдааны давуу эрэмбэ

`ERROR_NO_FROM → ERROR_FROZEN → ERROR_NO_TO → ERROR_SAME_ACCOUNT → ERROR_BAD_AMOUNT → ERROR_INSUFFICIENT → ERROR_LIMIT`

**Үндэслэл:** хүсэлтийг «хэн илгээх → хэнд → хэдийг» гэсэн байгалийн урсгалаар шалгаж, дүнгийн дотор эхлээд мэдээллийн сангүйгээр шалгах статик нөхцөлийг (≤ 0), дараа нь мөнгө бодитоор байгаа эсэхийг (үлдэгдэл), хамгийн сүүлд банкны бодлогын хязгаарыг (өдрийн лимит) шалгадаг гэж үзэв.

### Тестийн орчны бэлтгэл (fixture)

Төлөөлөх утгуудыг бодит болгохын тулд тест эхлэхээс өмнө дараах өгөгдлийг бэлдэнэ:

| ID | Валют | Төлөв | Үлдэгдэл | Өдрийн лимит |
|---|---|---|---|---|
| `ACC-M1` | MNT | идэвхтэй | 1 000 000₮ | 2 000 000₮ |
| `ACC-M2` | MNT | идэвхтэй | 0₮ | 2 000 000₮ |
| `ACC-U1` | USD | идэвхтэй | 500 USD | 1 000 USD |
| `ACC-FZ` | MNT | **царцаагдсан** | 1 000 000₮ | 2 000 000₮ |
| `ACC-FZ2` | MNT | **царцаагдсан** | 0₮ | 2 000 000₮ |
| `ACC-X` | — | **байхгүй** (DB-д ороогүй ID) | — | — |

Ханш тестийн орчинд тогтмол: **1 USD = 3 450₮** (ханш өөрчлөгдвөл хүлээгдэх үр дүн тогтворгүй болно).

### A1. Сонголт ба төлөөлөх утгууд

| Параметр | Сонголт | Төлөөлөх утга | Бодит жишээ |
|---|---|---|---|
| from | **F** — from дансны төлөв | F1 хүчинтэй (байгаа, идэвхтэй) | `ACC-M1` |
| | | F2 царцаагдсан | `ACC-FZ` |
| | | F3 байхгүй | `ACC-X` |
| to | **T** — to дансны төлөв | T1 хүчинтэй, from-оос өөр | `ACC-M2` |
| | | T2 байхгүй | `ACC-X` |
| | | T3 from-тэй ижил | `ACC-M1 → ACC-M1` |
| | | T4 байгаа ч царцаагдсан | `ACC-FZ2` |
| amount | **A** — дүнгийн тэмдэг | A1 эерэг | `100000` |
| | | A2 тэг | `0` |
| | | A3 сөрөг | `-500` |
| amount + орчин | **B** — хөрвүүлсэн дүн ба from-ийн үлдэгдэл | B1 үлдэгдлээс бага | 100 000₮ < 1 000 000₮ |
| | | B2 үлдэгдэлтэй яг тэнцүү | 1 000 000₮ |
| | | B3 үлдэгдлээс их | 1 000 001₮ |
| amount + орчин | **L** — хөрвүүлсэн дүн ба өдрийн *үлдсэн* лимит | L1 үлдсэн лимитээс бага | 100 000₮ < 500 000₮ |
| | | L2 үлдсэн лимиттэй яг тэнцүү | 500 000₮ (E2 үед) |
| | | L3 үлдсэн лимитээс их | 600 000₮ (E2 үед, үлдэгдлээс бага) |
| currency | **C** — хүсэлтийн валют ба from дансны валют | C1 ижил | `MNT` → MNT данс |
| | | C2 өөр (хөрвүүлэлт хийгдэнэ) | `USD` → MNT данс |
| currency + орчин | **R** — ханшийн чиглэл | R1 тоо хөрвүүлэхэд өснө (ханш > 1) | 20 USD → 69 000₮ |
| | | R2 тоо хөрвүүлэхэд багасна (ханш < 1) | 1 000 000₮ → 289.86 USD |
| *(далд орчин)* | **E** — өнөөдөр ашигласан лимит | E1 огт ашиглаагүй | 0 / 2 000 000₮ |
| | | E2 хэсэгчлэн ашигласан | 1 500 000 / 2 000 000₮ (үлдсэн 500 000₮) |
| | | E3 бүрэн дүүрсэн | 2 000 000 / 2 000 000₮ (үлдсэн 0₮) |

**Далд орчны сонголт бий юу?** Тийм. B, L, R, E нь хүсэлтийн body-д харагдахгүй — тэд мэдээллийн сангийн төлөв (үлдэгдэл, өнөөдөр ашигласан лимит) болон ханшаас хамаарна. Ялангуяа **E** (лимит хэр дүүрсэн) нь ижил `amount`-тай хоёр хүсэлтэд өөр үр дүн өгдөг. **R**-ийг тусад нь гаргасан шалтгаан: хөрвүүлэхээс *өмнөх* дүнгээр шалгадаг алдаа R1 үед ERROR_INSUFFICIENT-ийг алгасаж, R2 үед буруу ERROR_INSUFFICIENT гаргадаг — хоёр чиглэл өөр шинж тэмдэг өгнө.

**Тодорхойлолтын цоорхой (shift-left олдвор):** (1) to данс царцаагдсан байвал юу болох нь заагаагүй — T4-өөр шалгана; (2) танигдахгүй валютын код (`"XYZ"`), (3) талбар дутуу эсвэл `null` JSON, (4) 2-оос олон аравтын оронтой дүн — эдгээрт алдааны код тодорхойлогдоогүй тул загварт оруулаагүй, багш/PO-оос тодруулах асуулт болгон үлдээв.

### A2. Хязгаарлалтууд

`[error]` утга дангаараа алдаа буцаадаг тул бусадтай хослуулах нь утгагүй (эхний алдаа бусдыгаа нууна) — нэг фреймд л тестлэнэ. `[single]` нь алдаа биш ч онцгой/хилийн утга тул мөн нэг фреймд л тестлэнэ. `[property X]` / `[if X]` нь зөвхөн X шинж байгаа үед утга учиртай утгыг заана. *Фрейм* = сонголт бүрээс нэг утга авсан хослол (тест кейсийн загвар).

| Утга | Тэмдэглэгээ | Үндэслэл |
|---|---|---|
| F1 | — | Хэвийн утга, бусадтай чөлөөтэй хослоно. |
| F2 | `[error]` | ERROR_FROZEN-ийг үүсгэнэ; өөр алдаатай хослуулбал нэг алдаа нөгөөгөө нууна (masking) тул нэг удаа шалгахад хангалттай. |
| F3 | `[error]` | ERROR_NO_FROM — эрэмбийн хамгийн дээд алдаа тул ямар ч хослолд бусдыгаа далдална. |
| T1 | — | Хэвийн утга. |
| T2 | `[error]` | ERROR_NO_TO-г үүсгэх ганц нөхцөл. |
| T3 | `[error]` | ERROR_SAME_ACCOUNT-г үүсгэх ганц нөхцөл. |
| T4 | `[single]` | Тодорхойлолт зөвхөн from-ийн царцаалтыг хориглодог тул 201 хүлээгдэнэ; цоорхойг илрүүлэх зорилготой хилийн тохиолдол тул нэг удаа хангалттай. |
| A1 | `[property Positive]` | B, L сонголтууд зөвхөн эерэг дүнд утга учиртай тул тэдгээрийн нөхцөл болно. |
| A2 | `[error]` | `amount ≤ 0`-ийн хилийн утга → ERROR_BAD_AMOUNT. |
| A3 | `[error]` | Сөрөг дүн → ERROR_BAD_AMOUNT; зөвхөн `amount == 0` гэж шалгасан алдааг барина. |
| B1 | `[if Positive]` | Эерэг биш дүнг үлдэгдэлтэй харьцуулах нь утгагүй (BAD_AMOUNT түрүүлнэ). |
| B2 | `[if Positive]` `[single]` | «Хэтрэхгүй» = `≤` хилийн утга; `<` / `≤` off-by-one алдааг барихад нэг тохиолдол хангалттай. |
| B3 | `[error]` | ERROR_INSUFFICIENT-ийг үүсгэнэ. |
| L1 | `[if Positive]` | B1-тэй ижил шалтгаан. |
| L2 | `[if Positive]` `[single]` | Лимитийн `≤` хилийн утга, нэг удаа хангалттай. |
| L3 | `[error]` | ERROR_LIMIT-ийг үүсгэнэ (үлдэгдлээс бага дүнгээр, INSUFFICIENT-ээс тусгаарлаж). |
| C1 | — | Хэвийн утга. |
| C2 | `[property Converted]` | R сонголт зөвхөн хөрвүүлэлт хийгдэх үед утга учиртай. |
| R1 | `[if Converted]` | Валют ижил бол ханшийн чиглэл гэж байхгүй. |
| R2 | `[if Converted]` | R1-тэй ижил шалтгаан. |
| E1 | — | Хэвийн утга. |
| E2 | — | Хэвийн утга; L2/L3-ийг үлдэгдлээс бага дүнгээр тусгаарлаж шалгах боломж олгоно. |
| E3 | `[error]` | Үлдсэн лимит 0 тул ямар ч эерэг дүн ERROR_LIMIT өгнө — лимит «өмнөх гүйлгээгээр дүүрсэн» гэх өөр замаар шалгана. |

## Хэсэг B: PICT — pairwise covering array

> **Windows / Git Bash тэмдэглэл:** Git Bash нь `/o:3` гэх мэт `/`-ээр эхэлсэн аргументыг файлын зам гэж хөрвүүлдэг тул `MSYS_NO_PATHCONV=1` тавьж ажиллуулсан. Linux дээр шууд `pict browser.model /o:3` ажиллана.

### B1. Лекцийн браузерын жишээ

Модель: [`browser.model`](browser.model) — 6 параметр (3·3·2·2·2·2 = 144 бүрэн хослол).

```bash
pict browser.model | tee results/browser-2way.txt
MSYS_NO_PATHCONV=1 pict browser.model /o:3 > results/browser-3way.txt
tail -n +2 results/browser-2way.txt | wc -l    # 10
tail -n +2 results/browser-3way.txt | wc -l    # 20
```

| Хувилбар | Мөрийн тоо | Онолын доод хязгаар | Бүрэн олонлог | Хамралт |
|---|---|---|---|---|
| 2-way — [`results/browser-2way.txt`](results/browser-2way.txt) | **10** | 9 (Content × Cookies = 3·3) | 144 | 81/81 хос |
| 3-way — [`results/browser-3way.txt`](results/browser-3way.txt) | **20** | 18 (3·3·2) | 144 | 248/248 гурвал |

**2-way: яагаад 9 биш 10 вэ?** PICT хүснэгтийг greedy аргаар мөр мөрөөр байгуулдаг: мөр бүрт тухайн агшинд хамгийн олон шинэ хос хамрах утгуудыг сонгоод, өмнөх мөрүүдээ буцааж засдаггүй. Тиймээс эхний мөрүүд 15 шинэ хос хамарч байсан бол сүүлдээ тарсан «өнчин» хосууд үлдэж, 10-р мөр зөвхөн ганц хос (Content=Allow, Attacks=Yes)-ыг хамрахын тулд нэмэгдсэн — гараар лекц дээр 9 мөрөнд багтаасантай харьцуулахад 1 мөр илүү. Хамгийн цөөн мөртэй covering array олох нь NP-хэцүү бодлого тул PICT оновчтой байдлын оронд хурд ба давтагдах (детерминист) үр дүнг сонгодог; туршилтаар `/b:50` (50 өөр seed-ээс хамгийн цөөнийг авах) 9 мөр олсон нь 9 боломжтойг баталж байна (results/-д зөвхөн анхдагч гаралтыг хадгалав).

**3-way: 20 мөр vs бүрэн олонлог 144** — 86%-иар цөөн бөгөөд онолын доод хязгаар 18-аас ердөө 2 мөрөөр илүү.
